# SDD

SDD = Specification-Driven Development（规范驱动开发）

## 一、SDD 核心定义

SDD：用机器可读 / 可验证的规范，驱动整个开发流程。

- 先写规范（Specification）：明确系统 "应该做什么"
- 再写实现：满足规范
- 最后自动验证：检查实现是否符合规范

**和 TDD 的区别：**

- TDD：先写测试用例，关注 "行为是否正确"
- SDD：先写规范文档 / 模型，关注 "系统整体是否符合定义"

## 二、SDD 核心流程（标准 5 步）

1. **定义规范（Spec）**
   → 形式化/半形式化描述功能、接口、约束、不变量

2. **规范验证（Validate Spec）**
   → 检查规范是否矛盾、完整、可实现

3. **基于规范实现（Code）**
   → 代码必须严格对齐规范

4. **自动合规校验（Verify）**
   → 用工具证明实现符合规范

5. **持续维护规范（Sync）**
   → 代码与规范始终同步

**简单示例：** 先写接口规范 → 生成代码 / 测试 / 文档 → 校验实现是否匹配。

## 三、SDD 的优点

- **需求不漂移**：规范就是唯一真值
- **自动验证**：可工具化证明正确性
- **团队协作清晰**：前后端 / 测试 / 产品共用一份规范
- **高可靠性**：适合金融、航空、区块链、内核等关键系统
- **AI 编码超级适配**：AI 最擅长按规范生成合规代码

## 四、SDD 的缺点

- **前期成本高**：需要先编写规范，无法快速编码验证想法，小需求 / 原型开发效率低
- **灵活性受限**：需求频繁变更时，规范同步更新繁琐，易出现规范与代码不一致
- **工具依赖强**：优质 SDD 需配套工具链支撑，否则人工维护规范成本极高
- **不适用于探索性场景**：创新型、未知需求场景，难以提前制定完整规范
